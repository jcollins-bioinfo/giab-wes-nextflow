# M3 distribution and executable version identities

The M3 immutable tool lock uses schema version `2.0.0`. For each pinned image, `version` identifies the distribution release and `expected_reported_version` identifies the required executable self-report. Every run retains its actual version stdout and must match the latter field. There is no fallback between the two identities.

The pinned BWA-MEM2 Biocontainers distribution is release `2.3`, while its selected avx2 executable reports `2.2.1`. The official release source archive contains a `PACKAGE_VERSION` fallback of `2.2.1`, consistent with that observation. The lock records the archive hash and historical CI artifact hash with public source links. This observation describes a stale version report; it neither identifies the executed code as release 2.2.1 nor proves complete source-to-binary correspondence. Its initial CI run failed the former version gate and does not establish completed M3 acceptance.

BWA's version command must produce exactly one standalone numeric version line equal to `2.2.1` for this immutable image. A substituted `2.3`, a nearby version, an ambiguous pair of version lines, or a different image digest fails validation. The other five tools require an executable report matching their declared distribution release. No image digest changed for this repair.

M3 provenance schema `2.0.0` preserves `declared_version` as the distribution release and requires `expected_reported_version`, `version_note`, and `version_evidence_sources`. The latter sources explain the identity policy; the separate `version_evidence` artifact identifies the current run's stdout. Bundle validation rebinds the complete tool inventory, both versions, notes, sources, observed report and image identities to the installed package lock after checking the bundle hashes.

Only provenance and the tool lock advance to schema `2.0.0`; the other M3 evidence schemas remain exactly `1.0.0`. New required fields make this an incompatible contract change. Earlier provenance remains historical evidence under its original contract and is not silently rewritten or accepted by the current validator or publisher. A new, successful execution must produce current evidence. The project remains the same M3 development prerelease; this schema change does not claim a completed milestone or alter the scientific preprocessing policy.
